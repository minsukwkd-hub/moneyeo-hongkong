# 토끼의 여정 — 장기 구조와 데이터 모델 (v3)

작성 2026-10-14, 같은 날 비판 검토 1회 반영(개정 2). 사용자 결정 "장기 관점에서 가장 적절한 모델링으로 착수"에 따른 설계안. `CLAUDE.md`(규칙)·`작업기록.md`(이력)와 함께 읽는다. 구현이 진행되면서 갱신한다.

## 0. 한 줄 요약
- **로컬 우선(local-first) 단일 페이지 + 선택적 서버.** 모든 기능은 서버 없이 기기 안에서 완결되고, 서버는 "공유"와 "사진 보관"에만 쓴다.
- **서버는 Cloudflare 한 계정으로 통합**(Worker = 프록시·공유 API, D1 = 공유 코드, R2 = 사진). 이메일 인증이 풀릴 때까지 프록시는 Vercel, 인증이 풀리면 프록시부터 Cloudflare로 옮긴다.
- **모델을 먼저 정규화하고(저장소는 그대로), 기능은 작은 단계로 쌓는다.** 비동기 저장소(IndexedDB)는 사진이 들어오는 단계에서 사진에만 쓴다.

## 1. 목표 구조

```
[기기]  index.html (단일 파일) — 정식 실행 위치는 "홈 화면에 추가한 앱"
         ├ 화면: 지금 UI 뼈대 그대로 (탭·Day·지도·시트)
         ├ 데이터: localStorage  tokki-trip:<id> (여행 문서, 8~9KB/여행)
         │                      tokki-settings-v1 (프로필·연결·UI 상태·마지막 위치)
         │         IndexedDB    tokki/media (사진 blob, M3부터)
         └ SUZI: connect() 어댑터 (아티팩트 / 프록시 / 키)

[서버]  지금: Vercel Edge  https://suzi-proxy.vercel.app/api/suzi   (프록시만)
        목표: Cloudflare   Worker(프록시 + /share) · D1(공유 코드) · R2(사진)
        정적 호스팅은 GitHub Pages(출처 minsukwkd-hub.github.io) 유지.
```

왜 로컬 우선인가: 지인 소수가 쓰는 개인 서비스라 로그인·서버 장애·비용을 끌어들일 이유가 없다. 공유는 링크에 여정을 압축해 담는 것으로 시작하고, 사진처럼 링크에 못 담는 것만 서버로 보낸다.

왜 Cloudflare인가: Workers·D1·R2가 한 계정이고 무료 범위가 넓으며 R2는 전송료가 없다. 프록시 코드는 이미 있다(`suzi-proxy/worker.js`).

### 1.1 iOS 저장소 분리 — 반드시 지킬 운영 규칙
iOS에서는 **카카오톡 인앱 브라우저 / Safari 탭 / 홈 화면 앱**의 저장소가 서로 분리된다. 링크는 대부분 카카오톡으로 오므로, 아무 대책이 없으면 "카카오톡 안에서 가져온 여정이 Safari에는 없다", "홈 화면에 추가했더니 빈 앱이다"가 생긴다. 사진이 쌓이면 데이터 유실로 체감된다.
- **정식 실행 위치 = 홈 화면 앱.** Safari 탭의 7일 미사용 삭제도 홈 화면 앱은 피한다. 첫 안내에 "홈 화면에 추가"를 넣는다.
- 인앱 브라우저 감지(UA에 `KAKAOTALK`) 시 상단에 "Safari로 열기" 띠를 띄우고, **가져오기 버튼은 인앱에서 비활성화**한다. 카카오톡 외부 브라우저 스킴(`kakaotalk://web/openExternal?url=`)은 실기기에서 확인한다.
- 첫 실행 때 `navigator.storage.persist()`를 요청하고 결과를 settings에 기록한다.
- **정적 호스팅 출처를 바꾸지 않는다.** 출처가 바뀌면 모든 기기의 데이터가 사라진다. 바꿔야 하면 "내보내기 → 불러오기" 안내가 먼저다.
- Safari 탭 → 홈 화면 앱 이전 수단으로 "내보내기·불러오기"를 M1에 둔다.

## 2. 데이터 모델 v3

문서형(JSON). 여행 하나가 한 문서이고 날·일정·브릿지는 그 안에 들어간다. 사진만 별도 저장소(blob). `?`는 선택 필드.

### 2.0 공통 규칙
- **id**: `crypto.getRandomValues` 기반 8자 base36. 문서 안에서만 유일하면 된다. 가져오기·복사·템플릿 복제 때 항상 새로 발급. 템플릿(PLAN_A/B/C)은 id 없이 두고 복제 순간 부여.
- **버전**: Trip·settings·내보내기 파일·공유 페이로드 모두 `v`를 가진다. 모든 입력 경로(로컬 로드, 파일 불러오기, 링크 가져오기)는 같은 `migrate(doc)` 사다리(v2→v3→…)와 `validate(doc)`를 통과한다.
- **render는 데이터에 쓰지 않는다.** 지금 render가 각 항목에 `it.i`를 써 넣고 그대로 저장되는데, 이를 중단하고 지역 변수로 바꾼다(M1a).

### 2.1 Profile — 여행자 (settings 안)
```
{ name,                 // 여행자 이름. "SUZI의 여정", "SUZI에게 물어보기"에 쓰인다
  emoji? }
```
기기 1대 = 사람 1명 가정. 비어 있으면 첫 실행 시 묻고, 비어 있을 때 표시는 "토끼의 여정" / "물어보기". 이름 변경은 ⚙ 설정에서만 한다(SUZI 도구로 두지 않는다). **M0부터 `tokki-settings-v1.profile.name`에 저장**해 M1에서 다시 옮기지 않는다.

### 2.2 Trip — 여행 (문서의 뿌리)
```
{ id, v:3, title,                               // "모녀 홍콩 3박4일"
  dest:{ name:"홍콩·마카오", bounds, tz },
  dates:{ start?, end?, label? },                // ISO 날짜. 미정이면 label("11월 말 (미정)")만
  party:{ type:"모녀|가족|친구|혼자", members?:[{name, note?}], pace?:{stepsMax?}, interests?:[] },
  flights:{ in?:{code, dep, arr}, out?:{...} },  // dep/arr는 "현지 공항 기준 시각 문자열"
  lodging:[ { id, name, q, lat, lng, checkIn?, checkOut?, nights?, note? } ],
  days:[ Day ],
  ownerName?,                                    // 공유 링크에 실리는 여행자 이름
  templateId?, importedFrom?:{ ownerName, at, hash },
  createdAt, updatedAt, archived? }
```
`party`는 지금 SUZI 시스템 프롬프트에 상수로 박힌 "엄마와 딸, 하루 1~1.5만 보, 딤섬·애프터눈티"를 데이터로 옮긴 것이다. `RULES()`는 이 값으로 만든다.

### 2.3 Day
```
{ id, title, sub?, date?,                 // date는 dates.start에서 자동, 수동 덮어쓰기 가능
  region?, tags?:[],                      // 기존 Day.macau → tags:["마카오"]
  key?:{ name, why },                     // 템플릿 설명 전용 "오늘의 한 곳". 가져올 때 버린다
  items:[ Stop ],                         // 장소만. 시간순 자동 정렬 유지
  bridges:[ Bridge ],                     // 장소 사이 체크포인트. 장소 id에 붙는다
  expenses:[ Expense ],                   // 장소에 안 묶이는 지출
  journal?:{ text, mood?, updatedAt } }
```
Day에 id가 있어야 `swap_days` 뒤에도 사진·브릿지가 엉뚱한 날로 가지 않는다.

### 2.4 Stop — 장소 일정 (기존 item과 호환)
```
{ id,
  t, n, q, lat, lng, why?, note?, key?, hotel?,   // ← 기존 필드 그대로
  lodgingId?,                                     // hotel:true면 lodging[]의 id
  origin?:"template|me|suzi",                     // 기존 added/by를 대체
  dur?,                                           // 머무는 시간(분). 없으면 종류별 기본값
  travel?:{ mode:"walk|mtr|taxi|ferry|bus", min, src:"auto|manual" },  // 다음 장소까지
  status?:"planned|visited|skipped", visitedAt?,
  memo?, cost?:{ amount, cur },
  photos?:[ mediaId ] }
```
"핵심 장소"의 정본은 `Stop.key`다. `Day.key`는 템플릿 문구 전용.

### 2.5 Bridge — 따뜻한 체크포인트
```
{ id, after: stopId | null,              // null = 그날 맨 앞
  text, icon?, done?, doneAt? }           // "비타민 챙겨먹기", "엄마 컨디션 확인하기"
```
**items에 섞지 않는다.** items는 시간순 자동 정렬이 전제라 시간 없는 브릿지를 섞으면 정렬·번호·지도 핀·SUZI 순번이 모두 깨진다. 브릿지는 장소 id에 붙어 있어 장소가 정렬로 이동해도 따라가고, 렌더할 때만 장소 사이에 끼워 그린다. 붙어 있던 장소가 삭제되면 앞 장소로 옮겨 붙는다. 기본 제안 문구는 `BRIDGE_PRESETS[party.type]`에서 고르고 사용자가 직접 쓴다.

### 2.6 Expense — 지출
Stop에 묶이면 `Stop.cost`, 아니면 `Day.expenses[{ id, amount, cur, memo?, t? }]`. 합계는 **통화별로만** 표시하고 환산하지 않는다.

### 2.7 Place / Info — 장소 사전 (목적지별)
```
Place { q, n, lat, lng, why?, note?, area, kind, custom? }
Info  { type, hours, fee, tip, site, siteName, src, upd, conf }   // 키 = q
```
내장 사전(`CATALOG`, `INFO`)은 그대로 두고, 사용자 추가 장소와 수정 오버레이는 localStorage `tokki-places-v1`에 둔다(지금의 `suzi-hk-info-v1` 계승). 조회는 `내장 + 오버레이`.

### 2.8 Media — 사진·첨부 (M3, 기기 저장)
```
{ id, tripId, dayId?, stopId?, mime, blob, thumb, w, h, takenAt?, caption?, createdAt }
```
- 저장본은 **긴 변 2048px JPEG(품질 0.8, 장당 약 0.5MB)** 와 썸네일 320px. 원본은 사진 앱에 남긴다.
- IndexedDB `tokki/media`. 장소를 지워도 사진은 즉시 지우지 않는다(undo 대비). 고아 사진 정리는 별도 메뉴.
- `navigator.storage.estimate()`로 남은 용량 표시.
- 서버 저장(R2)으로 가면 `blob` 대신 `url`.

### 2.9 Share — 공유 (M3)
받는 쪽도 같은 `CATALOG`·`INFO`를 내장하고 있으므로 설명문을 링크에 실을 필요가 없다. 기존 PLAN_A를 통째로 압축하면 약 4,500자지만, 참조형으로 줄이면 약 800자다(실측).

**슬림 포맷(v1)**
```
{ v:1, title, owner, dates:{start?,end?,label?}, party:{type},
  flights?, lodging?:[{name,q,lat,lng}],
  days:[ { title, date?, tags?,
           s:[ [t, q, k?] | {t,n,q,lat,lng,why?} ],   // 카탈로그 장소는 [시간, q, 핵심] / 사용자 장소는 통째로
           b:[ [afterIdx|null, text] ] } ] }
```
- 링크: `#s=<base64url(deflate-raw(JSON))>`. 사진·메모·지출·일기·id는 싣지 않는다. 가져올 때 id를 새로 발급한다.
- **1,800자를 넘으면 "파일로 보내기"(JSON을 공유 시트로)로 자동 전환.** 같은 단계(M3)에 넣어 서버 없이도 큰 여정을 보낼 수 있게 한다. 카카오톡·iMessage의 실제 링크 길이 한계는 2k·4k·8k 링크로 실기기 시험해 이 문서에 적는다.
- 가져오기 흐름: 열람(읽기 전용) → "내 여정으로 가져오기" → 새 Trip(`importedFrom{ownerName, at, hash}`) → `history.replaceState`로 해시 제거. 같은 hash를 또 가져오면 "이미 가져온 여정 열기"를 제안한다. 인앱 브라우저에서는 가져오기 대신 "Safari에서 열기" 안내.
- **링크 내용은 신뢰하지 않는다.** `validate`: lat/lng 범위, 문자열 길이 상한, 제어문자 제거, `site`는 http(s)만, 장소명은 SUZI 프롬프트에도 들어가므로 길이 제한.
- 공유할 때 항공편·숙소 포함 여부를 선택할 수 있게 한다(단체방 재전파 대비).
- `CompressionStream('deflate-raw')`는 iOS 16.4 이상. 미만이면 "iOS 업데이트 필요" 안내.
- 2차(Cloudflare): 사진 포함 공유나 큰 여정은 Worker `/share`에 올리고 짧은 코드로 연다. D1 `{code, json, createdAt, expiresAt}`.

### 2.10 저장소 배치
| 저장소 | 내용 | 키 |
|---|---|---|
| localStorage | Trip 문서 | `tokki-trip:<id>` |
| localStorage | 설정: `{v, profile, conn, last:{type:"template"|"trip", id}, ui, persisted?}` | `tokki-settings-v1` |
| localStorage | 사용자 장소·정보 오버레이 | `tokki-places-v1` |
| IndexedDB `tokki` / `media` | 사진 blob (index: tripId) | id |

Trip은 실측 8~9KB라 localStorage에 수십 개가 들어간다. 저장소 접근은 `repo.load/save/list/remove` 래퍼 하나로 감싸, 나중에 IndexedDB로 옮겨도 래퍼 안만 바뀌게 한다. 여러 탭 동시 편집은 `updatedAt` 비교로 경고만 한다.

## 3. 기존 데이터에서 v3로 옮기기
옛 키: `suzi-hk-plan-v1`(초기 A 저장본), `suzi-hk-plan-v2:<U|A|B|C>`, `suzi-hk-variant`, `suzi-hk-info-v1`, `suzi-hk-conn-v1`.

첫 실행 시 한 번:
0. 옛 키 전체를 `tokki-legacy-backup`(JSON 한 덩어리)으로 묶어 둔다. 실패하면 마이그레이션을 중단한다.
1. `suzi-hk-plan-v2:U` → Trip(title "나의 홍콩 여정", `origin` 보존).
2. `suzi-hk-plan-v2:A|B|C`(및 v1)는 **정규화 비교**로 수정 여부를 판정한다. `i`·`added`·`by`를 뺀 `(t,n,q,lat,lng,why,note,key)` 집합이 템플릿과 같으면 수정 없음으로 보고 Trip을 만들지 않는다. (지금은 한 번 열기만 해도 키가 생기고 `it.i`가 저장되므로 단순 비교는 항상 "다름"이 나온다.)
3. `suzi-hk-info-v1` → `tokki-places-v1`.
4. `suzi-hk-conn-v1` → settings.conn. `suzi-hk-variant` → settings.last: 수정 없는 A/B/C였다면 `{type:"template", id:"A"}`, U나 수정본이면 `{type:"trip", id}`.
5. 모든 쓰기가 끝난 뒤에만 `tokki-migrated-v3=1`을 적는다. 옛 키는 지우지 않는다.

템플릿의 의미 변경(아래 4장)은 M1이 아니라 **M2a**에서 한다. 지금은 SUZI가 A/B/C를 직접 고칠 수 있는데, 그 동작을 바꾸는 것은 모델 정규화와 별개의 동작 변경이기 때문이다.

## 4. 화면 구조 (UI 뼈대 유지)
- **여행 상세** = 지금 페이지 그대로.
- **여정 버튼 4개 유지.** 의미는 "내 여정 + 추천 여정(템플릿) 3개". 템플릿은 보기 전용이고 "바탕으로 직접 꾸미기"(지금 있는 복사 기능)가 가져오기다. 템플릿 보기 상태에서 SUZI 변경 도구는 `"템플릿이라 수정할 수 없어요. 먼저 '내 여정으로 가져오기'가 필요해요"`를 돌려주고, 가져오기는 별도 도구 `import_template(id)`로 두어 다음 질문부터 적용한다. (열린 질문 D-2: A를 고친 적 있는 사용자가 A를 누르면 템플릿인가 수정본인가 → 기본안: 수정본 Trip이 있으면 그것, 없으면 템플릿.)
- **여행 목록(홈)** = M3에서 추가. 여행이 1개뿐이면 바로 상세로 들어간다.
- 브릿지 카드 = Day 타임라인 안에서 Stop보다 낮고 연한 카드 한 줄 + 체크 동그라미.
- 여행자 이름 = 상단 소제목 "SUZI의 여정", SUZI 버튼 "SUZI에게 물어보기", 시트 제목 "SUZI, 무엇이든 물어보세요". 공유받은 여정을 볼 때는 보낸 사람 이름(ownerName), 가져온 뒤에는 내 이름. 토끼 도우미는 시스템 프롬프트에서 "토끼"로 자기를 부른다.
- 인앱 브라우저 안내 띠, "홈 화면에 추가" 안내(1.1).

## 5. 착수 순서 (작은 단계로)

## 6. SUZI 도구 (모델에 맞춰)
- **대상 지정을 순번(idx)에서 `stop_id`로 바꾼다.** 지금은 질문마다 시스템 프롬프트의 일정 JSON이 한 번만 만들어져, 같은 tool loop에서 `add_stop` 뒤의 `remove_stop(idx)`가 옛 순번으로 엉뚱한 장소를 건드릴 수 있다. `compactPlan`에 id를 싣고, 모든 변경 도구는 **변경 후 그날의 `[{id,t,n}]`를 tool_result로 돌려준다.**
- 추가 도구: `reorder_stops(day, ids[])`(id 집합이 그날과 정확히 같을 때만 실행) · `add_bridge(day, after_id|null, text)` · `add_place(n,q,lat,lng,why)` · `mark_visited(stop_id)` · `add_expense(day, stop_id?, amount, cur)` · `import_template(id)`. 한 호출로 여러 건을 처리할 수 있게 배열 인자를 허용한다(최대 6라운드 제한 대비).
- `set_trip_info`는 `dates{start,end,label}`·`party`·`flights`·`lodging`에 맞춰 스키마를 바꾼다. `choose_plan`은 M3에서 `list_trips` + `open_trip(trip_id)`로 바뀐다.
- 시스템 프롬프트는 여행자 이름·`party`·기본정보로 만든다. 상수 문구 제거.

## 7. 결정된 것 / 열린 것
결정됨
- 서비스 이름 "토끼의 여정", UI 뼈대 불변.
- 입력 이름 = 여행자 이름. 토끼 도우미는 이름 없이 토끼. 이름 변경은 ⚙에서만.
- 사진은 기기 저장 우선(축소본), 서버는 M4에서.
- 체크포인트는 브릿지 카드. 장소 id에 붙고 items에 섞지 않는다.
- 공유는 슬림 포맷 링크 + 길면 파일, 서버 코드는 M4.
- 프록시는 지금 Vercel, Cloudflare 인증이 풀리는 대로 이전.
- 정식 실행 위치는 홈 화면 앱. 정적 호스팅 출처 불변.

사용자 확인이 필요한 것 (D)
- D-1 가족 간 **동기화**(일행이 같은 여정을 각자 기기에서 함께 고치기)를 할 것인가. 한다면 지금 `rev`·삭제 표시 필드를 넣어 둔다. 기본안: 안 함(공유 스냅샷만).
- D-2 A/B/C를 고친 적 있는 사용자가 그 버튼을 누르면 수정본과 템플릿 중 무엇이 뜨나. 기본안: 수정본.
- D-3 사진이 기기에만 있는 동안 백업 책임: 정기 내보내기 알림을 넣을 것인가. 기본안: 여행 종료일 다음 날 1회 안내.
- D-4 여정 삭제·보관 시 사진 연쇄 삭제 규칙. 기본안: 보관은 유지, 삭제는 30일 뒤 사진 정리.
- D-5 지인 일행 기기의 최소 iOS 버전(공유 압축은 16.4 이상, 저장소 고정은 17 이상).

열림 (진행하며 확인)
- 홍콩 외 목적지의 지도: 지금은 내장 해안선만. 목적지가 늘면 타일 지도(OSM) 도입 여부.
- 기기 1대 = 사람 1명 가정. 한 기기를 가족이 같이 쓰면 프로필 여러 개가 필요한지.
- 카카오톡·iMessage 링크 길이 실측치. 카카오톡 외부 브라우저 스킴 동작.
- 날짜를 줄여 Day 수가 줄 때 넘치는 일정 처리(기본안: 마지막 날로 합치고 안내).
